# interview-evaluator — Architecture Overview

> **Audience:** Engineers, PMs, and reviewers coming in cold.
> **Reading time:** ~2 minutes. Read top-to-bottom before a design review or standup.
> This is NOT a setup guide — see `README.md` for that.

---

## 1. What This Service Does

`interview-evaluator` grades the **reasoning** a candidate shows during a CareerCafe mock interview — not their code. It evaluates whether the student articulated a sensible approach before they wrote anything, whether their final implementation matched what they described, and whether their answers to two follow-up questions demonstrated real understanding. The question of whether the SQL or Python code itself is actually correct is handled by two separate deterministic systems that already exist. This service never second-guesses those systems. Its job is purely semantic: did this person think clearly, and can they explain what they did?

---

## 2. The Full Interview Flow — End to End

Each question follows six steps. Only two of them involve an AI call — everything else is deterministic or template-driven.

**1. Question Shown**
The student sees a SQL or Python question in the CareerCafe frontend. Nothing happens on the backend yet. No AI call.

**2. Explain Approach** *(AI Call 1 fires here — in the background)*
Before touching the code editor, the student types or speaks their plan: what algorithm they'd use, why, and what tradeoffs they're aware of. The moment they submit their explanation and move to the editor, **AI Call 1** is dispatched in the background. It evaluates the approach against a rubric — checking for correctness of reasoning, awareness of edge cases, and any stated misconceptions. The student doesn't wait for this; they move straight to coding.

**3. Playground / Implement**
The student writes their code. For SQL, this runs through the `sql-rule-engine-node`. For Python, code runs inside a browser-based Web Worker using a pinned version of Pyodide, against a deterministic test suite. The student may run their code as many times as they like — **no additional AI calls are made during this step**, no matter how many runs happen.

**4. Final Submit — Evidence Gets Frozen**
When the student clicks Submit, the deterministic system records its final verdict: which tests passed, which failed, what errors appeared, how many times code was run. This evidence object is frozen and sent to this service. It cannot be changed after this point. No AI call at this step.

**5. Follow-up 1 and Follow-up 2** *(AI Call 2 fires after both are answered)*
Two curated follow-up questions are shown — pre-written per rubric, not generated by AI on the fly. After the student answers both, **AI Call 2** fires. It evaluates three things simultaneously in a single prompt: whether the student's explanation (from Step 2) is consistent with what they actually coded, whether Follow-up 1 was adequately answered, and whether Follow-up 2 was adequately answered. Bundling all three into one call is a deliberate cost and latency decision.

**6. Debrief**
The student sees their feedback. This page is built entirely from template logic — the service assembles the debrief from the structured evidence already collected in the previous steps. **No AI call happens here.** The LLM never writes free-form prose for the student. Debrief text is deterministic given the evidence.

> **Bottom line: exactly 2 AI calls per question, total. The number of code runs has zero effect on AI usage.**

## 4. The Trust Boundary ← Read This Section First

> **Rule: deterministic systems own correctness. The AI evaluator owns reasoning only.**

The SQL rule engine and the Pyodide test runner are the sole, final authority on whether a candidate's code is correct. The AI evaluator is explicitly prohibited from contradicting them. If Pyodide reports that 3 out of 5 tests failed, that is the truth — the LLM is never asked "but is the code actually right?". It is only asked "does what this person said they would do match what they ended up writing?" Those are completely different questions.

**Concrete example:** A candidate says they'll use a hash map for O(n) lookup, then writes a nested loop. Pyodide reports all tests passed (the brute force solution still works). The deterministic status is `pass`. The AI evaluator's job is to notice the *consistency gap* — the student claimed one approach and coded another — not to re-litigate whether the tests passed. The `pass` result from Pyodide is never touched.

This boundary is enforced structurally: the code-correctness fields in the evidence object are written by the deterministic systems before this service ever receives the payload, and this service has no write access to those fields.

## 5. What Gets Stored vs. What Gets Computed

| Value | Source | How |
|---|---|---|
| Approach criterion statuses (MET / PARTIAL / MISSING / INCORRECT) | LLM — AI Call 1 | Structured JSON output from the prompt |
| Consistency status (matched / contradicted / etc.) | LLM — AI Call 2 | Structured JSON output from the prompt |
| Follow-up statuses (MET / PARTIAL / MISSING / INCORRECT) | LLM — AI Call 2 | Structured JSON output from the prompt |
| Qualitative evidence strings ("candidate claimed X, code shows Y") | LLM — AI Call 2 | Free-text fields inside the structured output |
| **The 0–10 numeric score** | **Backend logic only** | Computed from the statuses above using a fixed formula |
| Hard score cap (max 4.0 if approach was wrong) | Backend logic only | A guard applied after scoring, not an LLM decision |
| Corrective tags (e.g. "missed-edge-case", "wrong-complexity") | Backend logic only | Rule-matched from evidence statuses and rubric metadata |
| Debrief text (what the student reads at the end) | Template engine | Pre-written sentences filled from evidence — no LLM |

> **The LLM never outputs a number. It never writes the debrief. It classifies — that's all.**

## 6. Scaling Posture

This service is stateless — every request carries all the evidence it needs, and nothing is held in memory between calls. It is sized for roughly 100 concurrent users today, which fits comfortably on a single small instance without any queuing infrastructure. The interfaces for the LLM provider, any future queue (e.g. BullMQ), and any future cache layer are defined as swappable modules in `src/llm/` and `src/queue/` — plugging them in later is a configuration and implementation fill-in, not a rewrite. No Redis, no queue, and no cache are running yet, and none will be added before there is a concrete measured reason to do so.
